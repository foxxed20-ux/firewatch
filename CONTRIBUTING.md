# Работа над FireWatch

Изменения должны сохранять воспроизводимость конкурсного инференса и согласованность модели, API и карты.

## Как предложить изменение

Ошибки, вопросы по запуску и предложения обсуждаются в разделе задач [репозитория GitVerse](https://gitverse.ru/hackrus.experts/kosmo-krasnoiarsk_4_th_try_106) или в [GitHub Issues](https://github.com/foxxed20-ux/firewatch/issues). Проверьте существующие обращения и создайте одну задачу на одну проблему. Для ошибки укажите версию или commit SHA, среду, шаги воспроизведения, ожидаемый и фактический результат. Прикладывайте минимальный пример и обезличенные журналы без токенов, пользовательских данных и конкурсных растров.

Крупное изменение архитектуры, входных данных или API сначала предложите в задаче. Для исправления опечатки или небольшой ошибки можно сразу открыть запрос на слияние из тематической ветки или форка в `main`. Укажите связанную задачу и заполните [шаблон запроса на слияние](docs/PULL_REQUEST_TEMPLATE.md).

При обсуждении и ревью соблюдайте [кодекс поведения](CODE_OF_CONDUCT.md). Уязвимости сообщайте приватно по [политике безопасности](SECURITY.md): Telegram [@F0XXED](https://t.me/F0XXED). Не публикуйте способы эксплуатации, секреты или персональные данные в открытых задачах.

## Небольшие проверяемые этапы

1. Уточните контракт затронутого компонента и посмотрите `git status`.
2. Создайте тематическую ветку, например `codex/api-artifacts`.
3. Меняйте один связный сценарий; согласуйте общие файлы с владельцем компонента.
4. Запустите подходящие проверки и просмотрите `git diff --check`.
5. Сделайте коммит с понятным результатом: `feat: ...`, `fix: ...`, `docs: ...`, `test: ...` или `chore: ...`.
6. Публикуйте завершённый этап вместе с описанием фактических проверок и ограничений.

Не переписывайте общую историю ради красивого графика. Коммиты отражают реальную работу: начальный импорт, реализация, исправление, проверка и документация. Не меняйте даты и авторов для имитации разработки.

Основной конкурсный репозиторий — [GitVerse](https://gitverse.ru/hackrus.experts/kosmo-krasnoiarsk_4_th_try_106), зеркало — [GitHub](https://github.com/foxxed20-ux/firewatch). Обе площадки сохраняют общую историю. Для описания изменения используйте [шаблон](docs/PULL_REQUEST_TEMPLATE.md): что изменилось, какие проверки выполнены, какие ограничения остались. Workflows находятся в `.github/workflows/` и `.gitverse/workflows/`; статус серверного запуска проверяется на соответствующей площадке.

## Ревью и принятие изменений

Сопровождающие команды `4_th_try` проверяют назначение изменения, совместимость контрактов, тесты и документацию. Для слияния требуется одобрение сопровождающего, отсутствие нерешённых замечаний по корректности или безопасности и успешные применимые проверки CI. Автор устраняет замечания в той же ветке; изменение требований обсуждается явно в запросе. Нельзя отключать проверки или ослаблять ожидаемый результат теста ради успешного CI.

Проект сопровождается командой конкурса без гарантированного SLA. Целевой срок первого ответа на обычное обращение — до пяти рабочих дней. Если ответа нет, добавьте одно напоминание в ту же задачу. Срок реализации зависит от сложности и доступности команды; срочность согласуется в обсуждении.

Прежде чем отправлять код, убедитесь, что вправе передать его на условиях [лицензии проекта](LICENSE). Укажите происхождение сторонних фрагментов и сохраните их уведомления. Условия конкурсных данных и сторонних компонентов перечислены в [THIRD_PARTY.md](THIRD_PARTY.md).

## Проверки по области изменений

| Область | Команда |
| --- | --- |
| Контракты модели и RLE | `python -m pytest -q tests/test_competition_contract.py tests/test_tree_contract.py tests/test_model_runtime_contract.py` |
| Формы CNN и loss; требуется PyTorch | `python -m pytest -q tests/test_training_shapes.py` |
| API и геообработка | `python -m pytest -q tests/service` |
| Веб-логика | `node --check web/app.js` и `node --test tests/frontend/core.test.cjs` |
| Публикуемый diff | `git diff --check` и `git diff --cached --check` |
| Ссылки и состав репозитория | `python tools/check_repository.py` после добавления файлов в индекс Git |

Тесты сервиса требуют `pytest` и `httpx` в дополнение к сервисным зависимостям. Для изменения пользовательского сценария выполните его в браузере с настоящим API. Для изменения model bundle нужен реальный инференс; одного unit-теста недостаточно.

## Читаемый код

Используйте осмысленные имена, небольшие функции и явные проверки границ. Комментарии объясняют причину решения или ограничение данных. Внешние контракты описываются docstring и схемами. Избегайте массового форматирования файлов, которые одновременно редактирует другой участник.

Python использует четыре пробела, web-файлы — два, кодировку UTF-8 и завершающий перевод строки. Существующие vendored-библиотеки не переформатируются.

## Пересборка документов

Редактируйте `docs/PROJECT_PASSPORT.md` и `docs/DOMAIN_RESEARCH.md`, затем пересоберите PDF командой `python tools/build_project_documents.py`. Текущий макет проверен на Windows с системным шрифтом Arial и `reportlab==4.4.9` (`python -m pip install reportlab==4.4.9`). После изменения текста проверьте каждую страницу: переносы, таблицы, ссылки и читаемость. Готовые PDF находятся в `output/pdf/` и содержат встроенные шрифты. Сборка презентации описана в [заметках к защите](docs/presentation/presentation.md).

## Что хранить вне Git

Не коммитьте `.env`, ключи, токены, `deploy/private/`, виртуальные окружения, базы заданий, тренировочные данные, исходные спутниковые растры, архивы и веса. Проверенные bundle и большие результаты публикуются отдельно с контрольными суммами и описанием происхождения.

Отобранные JSON-доказательства в `artifacts/` сохраняются побайтово: `.gitattributes` отключает для них преобразование переводов строк. Их SHA-256 может использоваться другим отчётом, поэтому переформатирование требует обновления связанных доказательств. Новые отчёты добавляйте по точному списку файлов, не всей папкой с экспериментами.

Не включайте анонимизированный test в карту и не используйте его для подбора параметров. Изменение формата входов/выходов требует синхронного обновления API, документации и контрактных тестов.
